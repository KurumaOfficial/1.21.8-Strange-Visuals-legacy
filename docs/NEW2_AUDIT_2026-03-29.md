# NEW2 Audit

Дата: 2026-03-29

## 1. Scope

- Объём: `335` Java-файлов в `src/client/java`.
- Покрытие: все файлы прогнаны через структурный и эвристический статический разбор; вручную глубоко разобраны hot path-модули рендера, HUD, частиц, blur/post-process и event bus.
- Цель: найти архитектурные проблемы, некачественный код и места, которые режут FPS, с приоритетом на оптимизацию без потери функционала и визуального качества.
- Ограничение: это статический аудит. Оценка влияния на FPS основана на коде и официальных рекомендациях Fabric/OpenGL/Java, а не на runtime-профайле.

## 2. Executive Summary

Основная проблема NEW2 не в одном конкретном шейдере, а в паттерне: мод часто делает дорогую работу прямо в render-phase, много раз сканирует мир, создаёт большое количество временных объектов, дублирует full-screen проходы и не использует кэши там, где они уже есть в проекте.

Самые тяжёлые точки:

1. `DashCubes` почти наверняка совпадает с описанным вами дропом FPS при "кубах".
2. `JumpCircle` делает raycast'ы прямо в рендере и может взрывать frame time.
3. `TargetESP` в новых режимах кубов/призраков создаёт очень дорогой CPU-side render path.
4. `Trails`, `ParticleUtil`, `PlayerParticles`, `WorldParticles`, `KillEffect` создают много мусора и смешивают update с render.
5. HUD (`WaterMark`, `ModuleListRenderer`, `FontDraw`, `FontRenderer`, `RenderUtil`) тратит много CPU на blur и перерасчёт текста каждый кадр.
6. `MaskedCosmosRenderer`, `BlockCosmosRenderer`, `ScreenFilterRenderer`, blur-стек и `GlState` размножают framebuffer copy/state query, что даёт дорогой постпроцесс даже при красивой картинке.

## 3. P0 Critical FPS Hotspots

### 3.1 DashCubes

Файл: `src/client/java/ru/strange/client/module/impl/world/DashCubes.java`

Почему это критично:

- `onUpdate` на каждом motion-событии сканирует кандидатов и спавнит новые кубы: строки `147-187`.
- `collectTrackedEntities()` перебирает `mc.world.getEntities()`: строки `237-263`.
- `getPlaceableAround()` использует тройной цикл и дорогое удаление дублей через `stream().noneMatch(...)`: строки `265-279`.
- `findRandomPointAboveSurface()` до `64` раз пытается найти точку и постоянно аллоцирует `Vec3d`: строки `324-344`.
- `onRender3D()` каждый кадр делает `stream/filter/collect`: строки `202-230`.
- Каждый куб отдельно гоняет matrix push/pop, translate/rotate/scale и ручную геометрию fill/outline: render-путь начинается после `202`.

Вывод:

- Это CPU-bound эффект, а не просто "слишком много пикселей".
- Самый вероятный источник просадки `450 -> 300 FPS`, о которой вы написали.

Что менять без потери визуала:

1. Вынести поиск точек спавна из каждого motion-event в throttled update, например раз в `2-4` тика.
2. Кэшировать допустимые позиции вокруг entity хотя бы на короткое окно времени.
3. Заменить `result.stream().noneMatch(...)` на `BlockPos.Mutable` + hash/set по координатам.
4. Убрать `stream/filter/collect` из render-path; держать готовый список видимых/живых кубов.
5. Добавить distance budget: далеко от игрока снижать частоту спавна, а не визуальный стиль.

### 3.2 JumpCircle

Файл: `src/client/java/ru/strange/client/module/impl/player/JumpCircle.java`

Почему это критично:

- Рендер проходит через `renderScans()`: строки `265-320`.
- Для каждого сегмента берутся `inner/outer/mid` точки, то есть несколько выборок на сегмент: строки `298-317`.
- `sampleSurfacePoint()` вызывает `resolveSurfaceY()`: строки `322-328`.
- `resolveSurfaceY()` делает `mc.world.raycast(...)`: строки `331-347`.
- Количество сегментов настраивается до `96`: строка `76`.

Вывод:

- В худшем случае это сотни raycast'ов за кадр на один активный scan.
- Это один из самых агрессивных FPS-killer'ов в проекте.

Что менять без потери визуала:

1. Сэмплировать поверхность один раз при создании scan и хранить ring cache.
2. Повторно raycast'ить только при сильном смещении origin или смене чанка.
3. Для анимации волны менять только Y-offset поверх уже известных точек.

### 3.3 TargetESP

Файл: `src/client/java/ru/strange/client/module/impl/player/TargetESP.java`

Почему это критично:

- Все режимы сводятся в один render hot path: строки `154-179`.
- Новый режим призраков делает длинные trig-циклы и billboard-transform'ы в двух проходах: строки `620-700`.
- Новый режим кубов гоняет цикл до `cubeCount`, много `sin/cos`, matrix push/pop, fill + line + glow на каждый куб: строки `766-875`.
- Старый режим кубов ещё и обновляет/спавнит частицы в render-path: строки `884-939`.

Вывод:

- Модуль очень эффектный визуально, но реализован как дорогой CPU-side animator.
- На больших значениях count он легко съедает миллисекунды frame time.

Что менять без потери визуала:

1. Один раз за кадр считать time-based синусы/косинусы и переиспользовать.
2. Забрать `VertexConsumer` из `immediate` вне внутреннего цикла.
3. Спавн/апдейт старых cube-particles вынести в update/tick.
4. Ввести LOD по дистанции: дальним target'ам не уменьшать стиль, а уменьшать count и glow-pass.

### 3.4 Trails

Файл: `src/client/java/ru/strange/client/module/impl/player/Trails.java`

Почему это критично:

- На движении игрока создаётся пачка новых объектов `DashCubic -> DashBase -> DashTexture`: строки `194-215`.
- `DASH_CUBICS_FILTERED()` делает `stream/filter/collect` на каждый render: строки `234-239`.
- Рендер идёт двумя полными проходами: основной и bloom: строки `241-274`.
- `DashTexture` копирует texture group'ы в новые `ArrayList`: строки `517-555`.

Вывод:

- Здесь боль в allocation pressure и дублирующих проходах.

Что менять без потери визуала:

1. Object pool для `DashCubic`, `DashBase`, `DashTexture`.
2. Не копировать списки текстур на каждый trail instance; держать shared immutable refs.
3. Объединить или условно отключать второй проход, если bloom визуально почти не даёт вклада.

### 3.5 ParticleUtil и производные эффекты

Файл: `src/client/java/ru/strange/client/utils/particle/ParticleUtil.java`

Почему это критично:

- `renderParticles()` двигает симуляцию прямо в рендере: строки `103-134`.
- FOV-culling закомментирован: строка `128`.
- `Particle.update()` создаёт новые `Vec3d` и `Box` практически на каждом апдейте: строки `259-307`.
- `Box` для частицы тоже строится через новые `Vec3d`: строки `194-197`, `303-307`.

Кто страдает сверху:

- `KillEffect`: `149-190`, `481-590`
- `PlayerParticles`: `138-176`, `190-197`
- `WorldParticles`: `105-168`

Вывод:

- Стоимость эффекта привязана к FPS, а не к tick-rate.
- Это усиливает лаги именно тогда, когда FPS уже начал падать.

Что менять без потери визуала:

1. Перенести физику в tick/update.
2. Вернуть culling по FOV/frustum.
3. Перейти на mutable particle data вместо постоянного создания новых `Vec3d`/`Box`.

### 3.6 Box

Файл: `src/client/java/ru/strange/client/module/impl/player/Box.java`

Почему это критично:

- Каждый кадр идёт проход по `mc.world.getEntities()`: строки `80-103`.
- На каждый entity есть FOV/visibility-проверки.
- `isVisible()` делает raycast: строки `165-179`.

Вывод:

- В пустом мире это терпимо.
- В crowded сценах модуль масштабируется плохо и быстро становится CPU-bottleneck.

Что менять без потери визуала:

1. Предварительно отсекать по distance² и типу entity.
2. Visibility cache на короткий TTL, а не raycast для каждого entity каждый кадр.

## 4. P1 Expensive Visual Systems

### 4.1 HUD и текст

Проблемные файлы:

- `src/client/java/ru/strange/client/utils/render/FontDraw.java`
- `src/client/java/ru/strange/client/renderengine/font/FontRenderer.java`
- `src/client/java/me/x150/renderer/fontng/GlyphBuffer.java`
- `src/client/java/ru/strange/client/module/impl/interfaces/hud/ModuleListRenderer.java`
- `src/client/java/ru/strange/client/module/impl/interfaces/WaterMark.java`
- `src/client/java/ru/strange/client/utils/render/RenderUtil.java`
- `src/client/java/ru/strange/client/module/api/Manager.java`

Проблемы:

- `FontDraw` создаёт новый `FontRenderer` на каждый draw и width-query: строки `23-25`, `47-49`.
- `FontRenderer` создаёт новый `GlyphBuffer` и в draw, и в width: строки `186-209`, `217-220`.
- Сам `GlyphBuffer` прямо говорит, что shape текста дорогой и buffer надо переиспользовать: `me/x150/renderer/fontng/GlyphBuffer.java`, строки `33-35`.
- `ModuleListRenderer` заново строит и сортирует список модулей по ширине текста каждый кадр: строки `133-146`.
- `WaterMark` на каждый кадр заново считает ширины сегментов и рисует blur-card: строки `213-235`, `266-329`.
- `RenderUtil.drawClientRect()` почти на каждый HUD-card запускает blur: строки `40-53`.
- `Manager.getModules()` возвращает `List.copyOf(modules)` на каждом вызове: строки `83-84`.

Вывод:

- HUD-path тратит CPU несоразмерно своей визуальной ценности.
- В проекте уже есть правильный задел (`CachedText`), но он почти не используется в горячем пути.

### 4.2 Full-screen shader/post-processing

Проблемные файлы:

- `src/client/java/ru/strange/client/renderengine/renderers/util/MaskedCosmosRenderer.java`
- `src/client/java/ru/strange/client/renderengine/renderers/util/BlockCosmosRenderer.java`
- `src/client/java/ru/strange/client/renderengine/renderers/util/ScreenFilterRenderer.java`
- `src/client/java/ru/strange/client/module/impl/other/ScreenFilters.java`
- `src/client/java/ru/strange/client/module/impl/player/Hat.java`
- `src/client/java/ru/strange/client/module/impl/player/HitBubble.java`
- `src/client/java/ru/strange/client/module/impl/world/BlockOutline.java`
- `src/client/java/ru/strange/client/module/impl/utilities/GPS.java`

Проблемы:

- `MaskedCosmosRenderer` делает отдельные capture/restore/capture-after copy-проходы: строки `125-140`.
- `BlockCosmosRenderer` делает тот же паттерн поверх block-specific эффекта: строки `138-166`.
- `ScreenFilterRenderer` каждый вызов копирует основной framebuffer в отдельную texture и потом композитит: строки `88-108`.
- `ScreenFilters` вызывает `renderer.render()` на screen-event без short-circuit для "почти нейтральных" параметров: строки `45-54`.
- Эти рендереры затем повторно используются в `Hat`, `HitBubble`, `BlockOutline`, `GPS`, из-за чего эффекты не шарят scene capture между собой.

Вывод:

- В проекте красивая визуальная система, но она не собрана в единый compositor.
- Несколько активных эффектов умножают стоимость друг друга.

### 4.3 Blur и GL-state snapshots

Проблемные файлы:

- `src/client/java/ru/strange/client/renderengine/renderers/util/GlState.java`
- `src/client/java/ru/strange/client/renderengine/renderers/util/LegacyBlurProcessor.java`
- `src/client/java/ru/strange/client/renderengine/renderers/util/KawaseBlur.java`

Проблемы:

- `GlState.push()` делает большой пакет `glGetInteger`, `glGetIntegerv`, `glIsEnabled`, `glGetBooleanv`: строки `44-89`.
- `LegacyBlurProcessor` поверх этого ещё руками снимает часть GL-state и blit'ит кадр: строки `91-129`.
- `KawaseBlur` содержит второй такой же snapshot path и дополнительные `glGetInteger` по texture binding'ам: строки `576-617`, `684-690`.

Вывод:

- Здесь сильно чувствуется историческое наслоение нескольких blur-подсистем.
- Стоимость размазывается по всему UI и post-process стеку.

## 6. Architecture and Code Quality Problems

### 6.1 Смешаны update и render responsibility

Наблюдается в:

- `ParticleUtil`
- `TargetESP` (старые кубы)
- `JumpCircle`
- `HitBubble`

Проблема:

- Логика симуляции зависит от FPS и удорожает кадр именно в момент, когда он должен быть максимально дешёвым.

### 6.2 Дублирование core-абстракций

Найдены дубликаты:

- `Animation` в `4` местах
- `Easing` в `3` местах
- `Easings` в `3` местах
- `Config` в `2` местах
- `Manager` в `2` местах

Вывод:

- Проекту не хватает единых опорных модулей.
- Это повышает стоимость поддержки и мешает централизованной оптимизации.

### 6.3 Reflection-based event bus на горячем пути

Файл: `src/client/java/ru/strange/client/event/EventManager.java`

- Вызов слушателей идёт через reflection: строки `91-117`.

Вывод:

- Это не самый тяжёлый баг относительно render-модулей.
- Но архитектурно это лишний overhead на постоянных событиях ввода/рендера.

### 6.4 "Optimization" модуль не оптимизирует сам мод

Файл: `src/client/java/ru/strange/client/module/impl/other/Optimization.java`

- Модуль по сути переключает vanilla options: строки `82-90`.

Вывод:

- Название обещает оптимизацию клиента, но самые дорогие custom render systems модуля он не трогает вообще.

### 6.5 Модульная инициализация перегружена глобальными singleton-паттернами

Файл: `src/client/java/ru/strange/client/Strange.java`

- Почти все manager'ы, config, font, pipeline, rpc и event-регистрация сходятся в одном boot-path: строки `262-288`.

Вывод:

- Из-за этого тяжело локально изолировать производительность конкретных подсистем и строить нормальную lifecycle-модель.

### 6.6 Признаки проблем с кодировкой/локализацией

Во многих файлах видны поломанные комментарии/строки в кириллице при чтении как UTF-8.

Вывод:

- Это не FPS-проблема напрямую.
- Но это ухудшает сопровождение и усложняет безопасную оптимизацию.

## 7. Prioritized Optimization Roadmap

### Stage 1

Цель: самые быстрые победы по FPS без потери визуала.

1. Переписать `DashCubes` вокруг cache + spawn budget + no-stream render path.
2. Убрать raycast-per-segment из `JumpCircle`.
3. Вынести update из render в `ParticleUtil`, `HitBubble`, `TargetESP` old cube mode.
4. Добавить distance/FOV/frustum-budget для `Box`, `TargetESP`, `Trails`, `PlayerParticles`, `WorldParticles`.

Ожидаемый эффект:

- Самый высокий шанс быстро вернуть большой кусок FPS в мире с активными визуальными модулями.

### Stage 2

Цель: разгрузить HUD и текстовый стек.

1. Сделать persistent `FontRenderer` по family/size.
2. Перевести width/draw на reuse `GlyphBuffer` или `CachedText`.
3. Кэшировать visible module list и text widths для `ModuleListRenderer`, `WaterMark`, HUD renderer'ов.
4. Заменить blur-per-widget на один общий blur capture за кадр.

### Stage 3

Цель: вычистить архитектуру render pipeline.

1. Свести `MaskedCosmosRenderer`, `BlockCosmosRenderer`, `ScreenFilterRenderer` к общей compositing-модели.
2. Убрать дубли blur-state snapshot'ов.
3. Свести animation/easing стек к одному набору реализаций.
4. Со временем заменить reflection event bus на pre-bound listeners.

## 10. Bottom Line

Если оптимизировать только один модуль, первым должен идти `DashCubes`.

Если оптимизировать систему правильно, а не точечно, порядок должен быть таким:

1. `DashCubes`
2. `JumpCircle`
3. `TargetESP`
4. `ParticleUtil` + зависящие от него эффекты
5. HUD/text/blur/post-process стек

Это даст максимальный шанс поднять FPS без потери визуальной составляющей, потому что основной выигрыш лежит не в урезании эффектов, а в переносе тяжёлой работы из render-path в заранее подготовленные кэши и update-phase.
